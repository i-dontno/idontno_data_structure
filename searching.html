What is Searching?

Every day we look for things: a name in our phone contacts, a word in a dictionary, a roll number in a results list. In computing, searching is the process of finding whether a given value is present in a collection of data and, if it is, where it is.

Definitions
  • The value we are looking for is called the key (or target).
  • The collection being searched is the search space — here, an array (Python list) of n elements.
  • A successful search finds the key and returns its position (index).
  • An unsuccessful search finds that the key is not present; by convention it returns −1.
  • The cost of a search is usually measured by the number of key comparisons.

Two strategies

🚶 Linear search

Start at the first element and check each one in turn until the key is found or the list ends. Like reading every name in an unsorted attendance sheet. Works on any list.

✂️ Binary search

Look at the middle element of a sorted list. If the key is smaller, throw away the right half; if larger, throw away the left half. Repeat. Like opening a dictionary in the middle.

A simple example

Find 56 in the sorted list below (11 elements):

512182331394756647288
  • Linear search checks 5, 12, 18, 23, 31, 39, 47, 56 → found after 8 comparisons.
  • Binary search checks 39 (middle; 56 is larger → go right), then 64 (go left), then 47 (go right), then 56 → found after 4 comparisons.

For 11 elements the difference is small. For a million elements, linear search may need 1,000,000 comparisons, binary search at most 20.

Real-world applications

📒 Dictionaries & phone books

Alphabetical order lets us “binary search” by opening near the middle and moving left or right.

🗄️ Databases

Indexes keep keys sorted (in B-trees) so records are found in logarithmic time instead of scanning every row.

🐞 Debugging

git bisect binary-searches the commit history to find the commit that introduced a bug.

🛒 Shopping lists & small data

For a short, unsorted list (a cart, a menu), a simple linear scan is fastest to write and fast enough.

🎮 Games

“Guess my number between 1 and 100” — the best strategy is binary search: never more than 7 guesses.

📈 Answer searching

Binary search on a numeric answer: square roots, the smallest capacity that works, the first bad version.

Core Concepts

2.1 Terminology

TermMeaning
Sequential searchAnother name for linear search: elements are examined in sequence.
Interval searchSearches that repeatedly shrink an interval of a sorted list, e.g. binary search.
low, highIndices marking the current search interval [low, high] in binary search.
midThe middle index: mid = (low + high) // 2 (integer division).
SentinelA copy of the key placed at the end of the array so that linear search's loop needs no end-of-array test.
Random accessReaching any element by index in O(1) time — true for arrays, false for linked lists. Binary search needs it.
Divide and conquerSolving a problem by reducing it to smaller sub-problems. Binary search reduces the problem to one half each time (also called decrease and conquer).
Internal vs external searchInternal: data fits in main memory (this post). External: data on disk, where structures such as B-trees are used.

2.2 Preconditions

Linear search needs…
  • Nothing special — sorted or unsorted.
  • Works on arrays and linked lists (only needs “next element”).
Binary search needs…
  • The data must be sorted (ascending in this post).
  • Random access to the middle element (an array / Python list).
  • A way to compare keys (<, =, >).

2.3 Why does halving give log n?

After each comparison, binary search keeps at most half of the remaining elements:

n → n/2 → n/4 → n/8 → … → 1 after k steps: n / 2k = 1 ⇒ k = log₂ n

So the number of comparisons grows like log₂ n. Precisely, binary search makes at most ⌊log₂ n⌋ + 1 comparisons (counting each three-way test “=, <, >” as one comparison). Doubling the data adds just one extra comparison.

Linear Search and Binary Search

3.1 Linear search

Step-by-step working

  1. Start with the first element (index 0).
  2. Compare it with the key. If they are equal, return the index — success.
  3. Otherwise move to the next element and repeat.
  4. If the end of the array is reached, return −1 — unsuccessful.

Algorithm (pseudocode)

1LINEAR-SEARCH(A, n, key)
2 for i ← 0 to n − 1 do
3 if A[i] = key then
4 return i // successful search
5 return −1 // unsuccessful search

Worked example

Variant: sentinel linear search

The normal loop does two tests per element: “is i < n?” and “is A[i] = key?”. Placing the key itself at the end (the sentinel) guarantees the loop stops, so the first test can be dropped. Same O(n) complexity, but fewer operations per element. After the loop, check whether we stopped at a real element or at the sentinel.

3.2 Binary search

Step-by-step working

  1. Set low = 0 and high = n − 1.
  2. While low ≤ high: compute mid = (low + high) // 2.
  3. If A[mid] = key → return mid (found).
  4. If key < A[mid] → the key can only be on the left: high = mid − 1.
  5. If key > A[mid] → the key can only be on the right: low = mid + 1.
  6. If the loop ends (low > high), the interval is empty → return −1.

Algorithm — iterative

1BINARY-SEARCH(A, n, key)
2 low ← 0; high ← n − 1
3 while low ≤ high do
4 mid ← ⌊(low + high) / 2⌋
5 if A[mid] = key then return mid
6 else if key < A[mid] then high ← mid − 1 // discard right half
7 else low ← mid + 1 // discard left half
8 return −1

Algorithm — recursive

1BIN-SEARCH-REC(A, key, low, high)
2 if low > high then return −1 // base case
3 mid ← ⌊(low + high) / 2⌋
4 if A[mid] = key then return mid
5 if key < A[mid] then return BIN-SEARCH-REC(A, key, low, mid − 1)
6 return BIN-SEARCH-REC(A, key, mid + 1, high)

Complexity Analysis

4.1 Linear search

  • Best case: key is the first element → 1 comparison → O(1).
  • Worst case: key is the last element or absent → n comparisons → O(n).
  • Average case (successful): if the key is equally likely to be at any of the n positions, the expected number of comparisons is
(1 + 2 + 3 + … + n) / n = n(n + 1) / 2n = (n + 1) / 2 ⇒ O(n)
  • Unsuccessful search: always n comparisons. Space: O(1).

4.2 Binary search

Each comparison halves the problem, giving the recurrence:

T(n) = T(n/2) + 1, T(1) = 1
T(n) = T(n/4) + 2 = T(n/8) + 3 = … = T(n/2k) + k
With n/2k = 1 ⇒ k = log₂ n ⇒ T(n) = log₂ n + 1 = O(log n)
  • Best case: key is at the first middle → O(1).
  • Worst case: ⌊log₂ n⌋ + 1 comparisons → O(log n) (both successful and unsuccessful).
  • Average case: about log₂ n − 1 comparisons → O(log n).
  • Space: iterative O(1); recursive O(log n) for the call stack.

Difference between Linear Search and Binary Search

5.1 Point-by-point comparison

BasisLinear searchBinary search
Also calledSequential searchHalf-interval / logarithmic search
Data requirementSorted or unsortedMust be sorted
Data structureArray or linked listArray (needs random access)
ApproachCheck elements one after anotherDivide and conquer: compare with middle, discard half
Elements examinedUp to all nAt most ⌊log₂ n⌋ + 1
Time (worst)O(n)O(log n)
Time (best)O(1) — first elementO(1) — middle element
SpaceO(1)O(1) iterative / O(log n) recursive
Comparison typeEquality only (=)Ordering needed (<, =, >)
ImplementationVery simpleSimple, but easy to get off-by-one errors
Best suited forSmall or unsorted data, one-off searches, linked listsLarge sorted data, many repeated searches
Insertions / deletionsEasy (no order to maintain)Must keep the array sorted: O(n) per insertion

5.2 Similarities

  • Both find whether a key is present and return its index (or −1).
  • Both have best case O(1) and use O(1) extra space when written iteratively.
  • Both work on arrays / Python lists and can be written iteratively or recursively.

5.3 Is sorting first worth it?

Binary search needs sorted data. Sorting costs about n log₂ n operations once. If you will search many times, the investment pays off; for a single search, linear search is cheaper.

Special Cases & Common Mistakes

6.1 Special cases

Unsorted dataWorksWrong answers: it may report “not found” for a key that is present. Try the “Unsorted” preset with key 91.
Descending orderWorksSwap the directions: go left when key > A[mid].
Linked listWorks, O(n)Reaching the middle takes O(n) → no benefit. Use a balanced BST or skip list instead.

6.2 Advantages and disadvantages

Linear search

✅ Works on any data and any structure; no preprocessing; simplest code; good for small n; finds all occurrences easily.

❌ Slow for large n (O(n)); every unsuccessful search scans the whole list.

Binary search

✅ Extremely fast, O(log n); predictable worst case; also gives the insertion point; basis of many algorithms (bisect, lower bound, answer search).

❌ Needs sorted data and random access; keeping data sorted makes insertion/deletion O(n); easy to write with off-by-one bugs.

6.3 Common mistakes

Mistake 1 — Binary search on unsorted data

In [42, 7, 91, 15, 63, 28, 3, 77, 50, 19], searching 91: mid = 4 (63) and 91 > 63, so binary search goes right — but 91 is at index 2 on the left. It reports “not found”. Always sort first (or use linear search).

Mistake 2 — Writing low = mid or high = mid

With while low <= high, the update must be mid + 1 / mid − 1. With low = mid, when low = high − 1 and the key is larger, mid equals low forever → infinite loop.

Mistake 3 — Off-by-one in the loop condition

while low < high (instead of ≤) skips the last remaining element: searching for 88 in our 11-element list would fail. The condition and the initial high (n − 1 vs n) must match: [low, high] closed interval ⇒ high = n − 1 and low ≤ high.

Mistake 4 — Integer overflow in mid

In C/Java, (low + high) / 2 can overflow when low + high exceeds the int range (a famous bug in Java's library, found in 2006). Write mid = low + (high − low) / 2. Python integers do not overflow, but the safe form is good practice.

Mistake 5 — Returning too early in linear search

Writing else: return -1 inside the loop returns after checking only the first element. Return −1 only after the loop finishes.

6.4 Important examination points

Remember for exams
  • Linear: best O(1), average (n + 1)/2 comparisons, worst n → O(n). Works on unsorted data.
  • Binary: requires sorted data + random access; mid = ⌊(low + high)/2⌋; worst ⌊log₂ n⌋ + 1 comparisons → O(log n).
  • Binary search recurrence: T(n) = T(n/2) + 1 ⇒ O(log n).
  • Recursive binary search uses O(log n) stack space; iterative uses O(1).
  • When tracing binary search, write a table of low, high, mid, A[mid] and the decision at each step.
  • On failure, low is the insertion point.

Python Implementation

All four programs are complete and runnable (Python 3.6+). The outputs shown are their real outputs.

linear_search.py
# Linear (Sequential) Search — works on ANY list, sorted or not.

def linear_search(arr, key):
    """Return (index of first match or -1, number of comparisons)."""
    comparisons = 0
    for i in range(len(arr)):
        comparisons += 1
        if arr[i] == key:
            return i, comparisons
    return -1, comparisons


def sentinel_linear_search(arr, key):
    """Put the key at the end so the loop needs no 'i < n' check."""
    n = len(arr)
    if n == 0:
        return -1
    last = arr[-1]
    arr[-1] = key                    # sentinel
    i = 0
    while arr[i] != key:             # guaranteed to stop at the sentinel
        i += 1
    arr[-1] = last                   # restore the original last element
    if i < n - 1 or last == key:
        return i
    return -1


def find_all(arr, key):
    """Indices of ALL occurrences of key."""
    return [i for i, x in enumerate(arr) if x == key]


if __name__ == "__main__":
    data = [34, 7, 23, 32, 5, 62, 14]
    for key in [5, 34, 40]:
        idx, comp = linear_search(data, key)
        status = f"found at index {idx}" if idx != -1 else "not found"
        print(f"Search {key:>2}: {status:<20} comparisons = {comp}")
    print("Sentinel search for 62 ->", sentinel_linear_search(data, 62))
    print("Sentinel search for 99 ->", sentinel_linear_search(data, 99))
    print("All positions of 3 in [3, 1, 3, 4, 3]:", find_all([3, 1, 3, 4, 3], 3))

binary_search.py
# Binary Search — the list MUST be sorted.
# Iterative version (prints a trace) and recursive version.

def binary_search(arr, key, trace=False):
    low, high = 0, len(arr) - 1
    step = 0
    while low <= high:
        mid = low + (high - low) // 2        # same as (low + high) // 2, no overflow
        step += 1
        if trace:
            print(f"  step {step}: low={low:>2} high={high:>2} mid={mid:>2} A[mid]={arr[mid]:>2}", end="  ")
        if arr[mid] == key:
            if trace:
                print("-> FOUND")
            return mid
        elif key < arr[mid]:
            if trace:
                print("-> key is smaller, search LEFT half")
            high = mid - 1
        else:
            if trace:
                print("-> key is larger, search RIGHT half")
            low = mid + 1
    if trace:
        print(f"  low={low} > high={high}: search space empty -> NOT FOUND")
    return -1


def binary_search_recursive(arr, key, low, high):
    if low > high:                            # base case: empty range
        return -1
    mid = (low + high) // 2
    if arr[mid] == key:
        return mid
    if key < arr[mid]:
        return binary_search_recursive(arr, key, low, mid - 1)
    return binary_search_recursive(arr, key, mid + 1, high)


if __name__ == "__main__":
    A = [5, 12, 18, 23, 31, 39, 47, 56, 64, 72, 88]
    print("A =", A)
    for key in [56, 20]:
        print(f"Search {key}:")
        print("  result:", binary_search(A, key, trace=True))
    print("Recursive search for 5  ->", binary_search_recursive(A, 5, 0, len(A) - 1))
    print("Recursive search for 88 ->", binary_search_recursive(A, 88, 0, len(A) - 1))

binary_variants.py
# Binary search variants for lists WITH DUPLICATES,
# and Python's built-in bisect module.

import bisect


def first_occurrence(arr, key):
    low, high, ans = 0, len(arr) - 1, -1
    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == key:
            ans = mid
            high = mid - 1          # keep looking on the LEFT
        elif key < arr[mid]:
            high = mid - 1
        else:
            low = mid + 1
    return ans


def last_occurrence(arr, key):
    low, high, ans = 0, len(arr) - 1, -1
    while low <= high:
        mid = (low + high) // 2
        if arr[mid] == key:
            ans = mid
            low = mid + 1           # keep looking on the RIGHT
        elif key < arr[mid]:
            high = mid - 1
        else:
            low = mid + 1
    return ans


def lower_bound(arr, key):
    """First index i with arr[i] >= key (insertion point)."""
    low, high = 0, len(arr)        # note: high = len(arr), loop while low < high
    while low < high:
        mid = (low + high) // 2
        if arr[mid] < key:
            low = mid + 1
        else:
            high = mid
    return low


if __name__ == "__main__":
    B = [2, 4, 4, 4, 7, 9, 9, 12]
    print("B =", B)
    f, l = first_occurrence(B, 4), last_occurrence(B, 4)
    print(f"4: first at {f}, last at {l}, count = {l - f + 1}")
    print("first occurrence of 5:", first_occurrence(B, 5))
    for key in [4, 5, 13]:
        print(f"lower_bound({key}) = {lower_bound(B, key)}   bisect_left = {bisect.bisect_left(B, key)}")
    i = bisect.bisect_left(B, 9)
    print("Using bisect to test membership of 9:", i < len(B) and B[i] == 9)

How the code works

  • On a match, first_occurrence remembers the index and keeps searching left; last_occurrence keeps searching right. Count = last − first + 1, still O(log n).
  • lower_bound uses a half-open interval [low, high) and returns the insertion point — the same value as bisect.bisect_left.
compare_searches.py
# Experiment: count comparisons of linear vs binary search.
# One "comparison" = one look at an element (a three-way test counts once).

def linear_count(arr, key):
    for i, x in enumerate(arr):
        if x == key:
            return i + 1
    return len(arr)


def binary_count(arr, key):
    low, high, c = 0, len(arr) - 1, 0
    while low <= high:
        mid = (low + high) // 2
        c += 1
        if arr[mid] == key:
            return c
        if key < arr[mid]:
            high = mid - 1
        else:
            low = mid + 1
    return c


print(f"{'n':>9} | {'linear worst':>12} {'linear avg':>10} | {'binary worst':>12} {'binary avg':>10}")
for n in [10, 100, 1000, 10000]:
    arr = list(range(0, 2 * n, 2))              # sorted, even numbers
    lin = [linear_count(arr, k) for k in arr]   # every successful search
    bin_ = [binary_count(arr, k) for k in arr]
    print(f"{n:>9} | {max(lin):>12} {sum(lin) / n:>10.1f} | {max(bin_):>12} {sum(bin_) / n:>10.2f}")

Practice & Assessment

Try each question yourself first, then open the answer.

8.1 Conceptual questions

Q1. Why can binary search not be applied to an unsorted array?
Binary search discards half of the array after comparing with the middle element. That is only valid if all smaller elements are on the left and all larger ones on the right — i.e. the array is sorted. On unsorted data it may discard the half that contains the key.
Q2. Derive the average number of comparisons for a successful linear search.
If the key is equally likely at positions 1…n, finding it at position i costs i comparisons. Average = (1 + 2 + … + n)/n = (n + 1)/2, which is O(n).
Q3. What is the maximum number of comparisons binary search needs for 1,000 elements? For 1,000,000?
⌊log₂ 1000⌋ + 1 = 9 + 1 = 10. ⌊log₂ 1,000,000⌋ + 1 = 19 + 1 = 20.
Q4. Why is binary search not useful on a linked list?
A linked list has no random access: reaching the middle node takes O(n) steps of following links, so each “halving” already costs linear time and the total becomes O(n).
Q5. When would you prefer linear search even though binary search is faster?
When the data is unsorted and will be searched only once or a few times (sorting would cost more), when n is very small, when the data is in a linked list, or when the data changes very often.
