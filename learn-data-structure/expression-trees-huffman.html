Introduction to Expression Trees

Definition

An expression tree is a binary tree that represents a mathematical expression. Every leaf holds an operand (a number or variable) and every internal node holds an operator. The tree's shape shows exactly which operation happens first, so no parentheses are needed.

Operands and operators

Operands

The values being worked on: 5, 3.14, A, x. They are stored in leaf nodes.

Operators

The actions: + - * / ^. They are stored in internal nodes, each with a left and a right child.

A first diagram

The expression (A + B) * (C - D) as a tree. Orange nodes are operators, green nodes are operands.

Expression tree for (A + B) * (C - D). The parentheses are not stored: the tree shape replaces them.

Why use expression trees?

  • No ambiguity: the structure fixes the order of evaluation.
  • Easy evaluation: a simple recursive postorder walk computes the value.
  • Easy conversion: the three traversals give infix, prefix and postfix forms.
  • Transformable: compilers can simplify or optimise a tree before generating code.

Relationship with binary trees

An expression tree is a special full binary tree: every node has either 0 children (operand) or exactly 2 children (binary operator). It uses the same Node structure (value, left, right) as any binary tree, and the same traversals.

Structure of an expression tree

Labelled tree for (A + B) * (C - D): the root is the operator that runs last; leaves are operands.

Reading a tree

Work from the bottom: the deepest operators run first. In this tree A + B and C - D are computed first, and their results are multiplied last.

Real-world applications

  • Compilers and interpreters (parsing code into an abstract syntax tree)
  • Scientific calculators and spreadsheet formulas
  • Database query processing (query plans are trees)
  • Computer algebra systems (simplifying and differentiating formulas)

Types of Expression Notations

The same expression can be written in three ways. They differ only in where the operator is placed.

A. Infix notation

The operator is between its operands: A + B. This is the everyday way we write maths. It needs precedence and associativity rules, plus parentheses.

OperatorPrecedenceAssociativity
^Highest (3)Right to left: 2^3^2 = 2^(3^2) = 512
*, /Middle (2)Left to right: 8/4/2 = (8/4)/2 = 1
+, -Lowest (1)Left to right: 10-4-3 = (10-4)-3 = 3

B. Prefix notation (Polish notation)

The operator comes before its operands: + A B. No parentheses are needed. Evaluate by scanning right to left.

C. Postfix notation (Reverse Polish notation)

The operator comes after its operands: A B +. No parentheses needed. Evaluate by scanning left to right with a stack. Many calculators use it.

Constructing an Expression Tree

A. From postfix notation

Algorithm

Scan the tokens left to right with a stack of trees.
1. Operand → make a leaf node and push it.
2. Operator → pop two nodes: the first pop is the right child, the second pop is the left child. Make a new operator node with these children and push it.
3. At the end, exactly one node remains: the root.

Dry run for A B + C D - *. The stack holds whole subtrees; here they are shown as text:

tokens = "A B + C D - *".split()
stack = []
for t in tokens:
    if t in "+-*/":
        right = stack.pop()
        left = stack.pop()
        stack.append(f"({left} {t} {right})")     # shown as text; a real tree node in the program
    else:
        stack.append(t)
    print(f"read {t!r:4} -> stack: {stack}")

C. From infix notation

Infix cannot be scanned directly because of precedence and parentheses. First convert it to postfix with the shunting-yard algorithm, then build the tree as in part A.

Infix → postfix rules

1. Operand → send to the output.
2. ( → push on the stack.
3. ) → pop to the output until ( is found; discard it.
4. Operator → pop operators of higher or equal precedence (for ^: only higher) to the output, then push the new operator.
5. At the end, pop everything left to the output.

expr = "(A + B) * (C - D)"
prec = {"+": 1, "-": 1, "*": 2, "/": 2}
output, stack = [], []
print(f"{'token':6}{'stack':8}output")
for t in expr.replace("(", " ( ").replace(")", " ) ").split():
    if t == "(":
        stack.append(t)
    elif t == ")":
        while stack[-1] != "(":
            output.append(stack.pop())
        stack.pop()
    elif t in prec:
        while stack and stack[-1] != "(" and prec[stack[-1]] >= prec[t]:
            output.append(stack.pop())
        stack.append(t)
    else:
        output.append(t)
    print(f"{t:6}{' '.join(stack):8}{' '.join(output)}")
while stack:
    output.append(stack.pop())
print("postfix:", " ".join(output))

Role of the stack

In postfix construction the stack holds finished subtrees waiting for their operator. In infix → postfix the stack holds operators and parentheses waiting for their turn. Both rely on last-in, first-out order.

Evaluating an expression tree

Recursive rule

Leaf → return its value.
Operator node → evaluate the left subtree, evaluate the right subtree, then apply the operator to the two results.
This is a postorder process: children first, operator last.

Example: (5 + 3) * (10 - 2). The orange note beside each node is its computed value.

Evaluation: 5 + 3 = 8, 10 − 2 = 8, then 8 × 8 = 64.

The same walk in code, printing each computation (indentation shows the depth):

def evaluate_verbose(node, depth=0):
    pad = "  " * depth
    if node.left is None and node.right is None:
        print(f"{pad}leaf {node.value} -> {node.value}")
        return int(node.value)
    a = evaluate_verbose(node.left, depth + 1)       # left subtree first
    b = evaluate_verbose(node.right, depth + 1)      # then right subtree
    result = {"+": a + b, "-": a - b, "*": a * b}[node.value]   # operator last: postorder
    print(f"{pad}{a} {node.value} {b} = {result}")
    return result

Logic: a stack of nodes. Operand → push a leaf. Operator → pop right, pop left, push a new node. Validate the counts.

def build_from_postfix(tokens):
    stack = []
    for token in tokens:
        if token in OPERATORS:
            if len(stack) < 2:
                raise ValueError(f"Invalid expression: operator '{token}' needs two operands")
            right = stack.pop()           # the LAST operand pushed is the right child
            left = stack.pop()
            stack.append(Node(token, left, right))
        else:
            stack.append(Node(token))     # operand -> leaf node
    if len(stack) != 1:
        raise ValueError("Invalid expression: operands and operators do not match")
    return stack[0]

PRECEDENCE = {"+": 1, "-": 1, "*": 2, "/": 2, "^": 3}
RIGHT_ASSOCIATIVE = {"^"}

def tokenize(expr):
    return re.findall(r"\d+\.?\d*|[A-Za-z_]\w*|[-+*/^()]", expr)

def infix_to_postfix(expr):
    output, stack = [], []
    for token in tokenize(expr):
        if token == "(":
            stack.append(token)
        elif token == ")":
            while stack and stack[-1] != "(":
                output.append(stack.pop())
            if not stack:
                raise ValueError("Mismatched parentheses")
            stack.pop()                    # discard the "("
        elif token in PRECEDENCE:
            while (stack and stack[-1] != "(" and
                   (PRECEDENCE[stack[-1]] > PRECEDENCE[token] or
                    (PRECEDENCE[stack[-1]] == PRECEDENCE[token] and token not in RIGHT_ASSOCIATIVE))):
                output.append(stack.pop())
            stack.append(token)
        else:
            output.append(token)           # operand goes straight to the output
    while stack:
        top = stack.pop()
        if top == "(":
            raise ValueError("Mismatched parentheses")
        output.append(top)
    return output

Logic: postorder recursion. Leaves are converted to numbers (or looked up in a variables dictionary); operator nodes combine the two child results.

def evaluate(node, variables=None):
    if node is None:
        raise ValueError("Cannot evaluate an empty tree")
    if node.left is None and node.right is None:             # leaf: an operand
        token = node.value
        if variables and token in variables:
            return variables[token]
        try:
            return float(token) if "." in token else int(token)
        except ValueError:
            raise ValueError(f"Unknown operand: {token!r}")
    a = evaluate(node.left, variables)                        # evaluate left subtree
    b = evaluate(node.right, variables)                       # evaluate right subtree
    if node.value == "+": return a + b
    if node.value == "-": return a - b
    if node.value == "*": return a * b
    if node.value == "/":
        if b == 0:
            raise ZeroDivisionError("Division by zero in expression")
        return a / b
    if node.value == "^": return a ** b
    raise ValueError(f"Unknown operator: {node.value!r}")

Introduction to Huffman Coding

Definition

Huffman coding is a lossless data compression algorithm that gives shorter binary codes to frequent characters and longer codes to rare ones. It builds the best possible set of such codes (an optimal prefix code) from the character frequencies, using a binary tree.

Real-world intuition

Think of Morse code: the common letter E is a single dot, while the rare Q is four symbols. Messages become shorter because frequent letters are cheap. Huffman coding does the same with bits, but calculates the best codes for your data.

Why is it needed?

Normally every character takes a fixed 8 bits (ASCII). The text AAAAABBBCCDDE has 13 characters, so it needs 104 bits. If A (very frequent) gets a 2-bit code and E (rare) a 3-bit code, the same text needs only 29 bits.

Key terms

  • Lossless compression: the original data can be rebuilt exactly from the compressed data.
  • Fixed-length encoding: every symbol uses the same number of bits (ASCII: 8).
  • Variable-length encoding: different symbols use different numbers of bits.
  • Frequency-based encoding: frequent symbols get shorter codes, so the average length drops.

Why prefix-free matters

With codes A=0, B=01, C=1 the string 01 could be B or AC. A prefix-free code removes this ambiguity: you always know when a code ends. Huffman trees guarantee it because characters sit only on leaves.

How Huffman Coding Works

The algorithm

  1. Count the frequency of every character.
  2. Create a leaf node for each character.
  3. Put all nodes in a min-priority queue ordered by frequency.
  4. Remove the two nodes with the lowest frequency.
  5. Create a parent node whose frequency is their sum (the two removed nodes become its children).
  6. Insert the parent back into the queue.
  7. Repeat steps 4 to 6 until one node remains: the root.
  8. Walk the tree to assign codes: left = 0, right = 1.

A. Generating the codes

Start at the root with an empty string. Going left appends 0, going right appends 1. When you reach a leaf, the string collected is that character's code.

def build_huffman_tree(text):
    if not text:
        return None
    freq = Counter(text)                                   # B. frequency table
    heap = []
    for order, (ch, f) in enumerate(freq.items()):         # C. min-priority queue
        heapq.heappush(heap, (f, order, HuffNode(ch, f)))
    order = len(heap)                                      # tie-breaker keeps nodes from being compared

        f2, _, right = heapq.heappop(heap)                 # second smallest
        heapq.heappush(heap, (f1 + f2, order, HuffNode(None, f1 + f2, left, right)))

Greedy Approach, Applications, Complexity & Trade-offs

A. Why Huffman coding is greedy

Greedy algorithm

A greedy algorithm builds a solution step by step, always taking the choice that looks best right now, and never undoes it. It works when the local best choice also leads to a global best answer.

Huffman's local choice: merge the two nodes with the smallest frequencies. They are the rarest symbols, so they should get the longest codes, deep at the bottom of the tree. Merging them costs the least extra weight.

import heapq
def merge_cost(freqs):
    heap = list(freqs)
    heapq.heapify(heap)
    total = 0
    while len(heap) > 1:
        a = heapq.heappop(heap)
        b = heapq.heappop(heap)
        print(f"  merge {a} + {b} = {a + b}")
        total += a + b                 # each merge adds its weight to the total cost
        heapq.heappush(heap, a + b)
    return total

merging the two SMALLEST each time: 29  (the Huffman choice)

Why the result is optimal

  • Exchange argument: in an optimal tree the two rarest symbols can be swapped to the deepest level as siblings without making the total worse. So some optimal tree has them as siblings.
  • After merging them into one node, the remaining problem is the same kind of problem with one fewer symbol, so the argument repeats.
  • Therefore the greedy choice at every step is safe, and the final code has the minimum possible total length for prefix codes.

How it differs from other greedy algorithms: Kruskal and Prim also pick the cheapest edge each time, and activity selection picks the earliest finishing job. Huffman instead repeatedly combines items bottom-up into a tree, and its measure of cost is the weighted path length.

B. Applications

File and text compression

Huffman coding is a core step in tools like gzip and ZIP (inside the DEFLATE method).

Image compression

PNG uses DEFLATE; JPEG uses Huffman codes to store quantised coefficients.

Multimedia

Audio formats such as MP3 use Huffman tables for the final encoding step.

Data transmission

Fewer bits to send means faster transfers and lower bandwidth.

Communication systems

Frequency-aware codes reduce traffic for messages with skewed symbol frequencies.

Compression pipelines

Often paired with LZ77 or transforms; Huffman is one component, not the whole method.

A component, not the whole story

Real formats rarely use Huffman coding alone. JPEG first applies a transform and quantisation (which is lossy) and then uses Huffman coding on the result. ZIP and PNG first find repeated strings (LZ77) and then Huffman-code them. The Huffman step itself is always lossless.

C. 15 interview questions

Q1. What is an expression tree?

A binary tree that represents an arithmetic expression: leaf nodes are operands (numbers or variables) and internal nodes are operators. The structure itself encodes precedence, so no parentheses are needed.

Q2. How is an expression tree constructed?

From postfix: scan left to right, push operands as leaf nodes, and when you see an operator pop two nodes (first pop = right child, second = left child), make a new node and push it. From prefix: scan right to left with the left/right order swapped. From infix: convert to postfix first (shunting-yard), then build.

Q3. What is the relationship between tree traversals and notations?

Inorder gives infix (with parentheses), preorder gives prefix, and postorder gives postfix.

Q4. How do you evaluate an expression tree?

Recursively: a leaf returns its value; an operator node evaluates its left and right subtrees and applies the operator. This is a postorder traversal and takes O(n) time.

Q5. Why are stacks used to build expression trees?

Operands must wait until their operator arrives, and the operator always uses the most recently built subtrees. That last-in, first-out behaviour is exactly a stack.

Q6. Why does infix need parentheses but postfix and prefix do not?

In infix the order of evaluation depends on precedence and associativity, so parentheses override it. In prefix and postfix the position of each operator already fixes the evaluation order.

Q7. What is Huffman coding?

A lossless compression technique that gives shorter binary codes to frequent characters and longer codes to rare ones. It builds an optimal prefix code from character frequencies using a binary tree.

Q8. Why is Huffman coding called a greedy algorithm?

At every step it makes the locally best choice (merge the two lowest-frequency nodes) and never reconsiders it. This choice is provably optimal for building a prefix code.

Q9. What is a prefix-free code?

A set of codes in which no code is the beginning of another. Because of this, a bit string can be decoded in exactly one way without separators.

Q10. Why is a min-heap used in Huffman coding?

We repeatedly need the two smallest frequencies. A min-heap gives each in O(log k) instead of sorting again and again.

Q11. How does Huffman decoding work?

Start at the root. Read bits: 0 means go left, 1 means go right. When you reach a leaf, output its character and return to the root.

Q12. Is Huffman coding lossless?

Yes. Decoding gives back exactly the original data, provided the decoder has the same tree or code table.

Q13. What happens when two characters have equal frequencies?

Either may be picked first, so several different Huffman trees and code sets are possible. All of them are optimal: the total encoded length is the same.

Q14. What is the time complexity of Huffman tree construction?

O(k log k), where k is the number of distinct characters: k - 1 merges, each with heap operations costing O(log k). Counting frequencies adds O(n).

Q15. Which is better for a single-character input and why does it need special handling?

The tree has just one leaf, so the usual rule gives an empty code. Assign it the code 0 so that the encoded length is not zero and decoding still works.

class Node:
    def __init__(self, value, left=None, right=None):
        self.value = value        # an operator or an operand
        self.left = left          # left child
        self.right = right        # right child

OPERATORS = {"+", "-", "*", "/", "^"}

def build_from_postfix(tokens):
    stack = []
    for token in tokens:
        if token in OPERATORS:
            if len(stack) < 2:
                raise ValueError(f"Invalid expression: operator '{token}' needs two operands")
            right = stack.pop()           # the LAST operand pushed is the right child
            left = stack.pop()
            stack.append(Node(token, left, right))
        else:
            stack.append(Node(token))     # operand -> leaf node
    if len(stack) != 1:
        raise ValueError("Invalid expression: operands and operators do not match")
    return stack[0]

def build_from_prefix(tokens):
    stack = []
    for token in reversed(tokens):        # scan from right to left
        if token in OPERATORS:
            if len(stack) < 2:
                raise ValueError(f"Invalid expression: operator '{token}' needs two operands")
            left = stack.pop()            # scanning right-to-left: first popped is the LEFT child
            right = stack.pop()
            stack.append(Node(token, left, right))
        else:
            stack.append(Node(token))
    if len(stack) != 1:
        raise ValueError("Invalid expression: operands and operators do not match")
    return stack[0]

PRECEDENCE = {"+": 1, "-": 1, "*": 2, "/": 2, "^": 3}
RIGHT_ASSOCIATIVE = {"^"}

def tokenize(expr):
    return re.findall(r"\d+\.?\d*|[A-Za-z_]\w*|[-+*/^()]", expr)

def infix_to_postfix(expr):
    output, stack = [], []
    for token in tokenize(expr):
        if token == "(":
            stack.append(token)
        elif token == ")":
            while stack and stack[-1] != "(":
                output.append(stack.pop())
            if not stack:
                raise ValueError("Mismatched parentheses")
            stack.pop()                    # discard the "("
        elif token in PRECEDENCE:
            while (stack and stack[-1] != "(" and
                   (PRECEDENCE[stack[-1]] > PRECEDENCE[token] or
                    (PRECEDENCE[stack[-1]] == PRECEDENCE[token] and token not in RIGHT_ASSOCIATIVE))):
                output.append(stack.pop())
            stack.append(token)
        else:
            output.append(token)           # operand goes straight to the output
    while stack:
        top = stack.pop()
        if top == "(":
            raise ValueError("Mismatched parentheses")
        output.append(top)
    return output

def inorder(node):                          # Left, Root, Right
    if node is None:
        return ""
    if node.left is None and node.right is None:
        return str(node.value)
    return "(" + inorder(node.left) + " " + node.value + " " + inorder(node.right) + ")"

def preorder(node):                         # Root, Left, Right
    if node is None:
        return []
    return [node.value] + preorder(node.left) + preorder(node.right)

    if node is None:
        return []

def evaluate(node, variables=None):
    if node is None:
        raise ValueError("Cannot evaluate an empty tree")
    if node.left is None and node.right is None:             # leaf: an operand
        token = node.value
        if variables and token in variables:
            return variables[token]
        try:
            return float(token) if "." in token else int(token)
        except ValueError:
            raise ValueError(f"Unknown operand: {token!r}")
    a = evaluate(node.left, variables)                        # evaluate left subtree
    b = evaluate(node.right, variables)                       # evaluate right subtree
    if node.value == "+": return a + b
    if node.value == "-": return a - b
    if node.value == "*": return a * b
    if node.value == "/":
        if b == 0:
            raise ZeroDivisionError("Division by zero in expression")
        return a / b
    if node.value == "^": return a ** b
    raise ValueError(f"Unknown operator: {node.value!r}")

import heapq
from collections import Counter

class HuffNode:
    def __init__(self, char, freq, left=None, right=None):
        self.char = char          # None for internal nodes
        self.freq = freq
        self.left = left
        self.right = right

def build_huffman_tree(text):
    if not text:
        return None
    freq = Counter(text)                                   # B. frequency table
    heap = []
    for order, (ch, f) in enumerate(freq.items()):         # C. min-priority queue
        heapq.heappush(heap, (f, order, HuffNode(ch, f)))
    order = len(heap)                                      # tie-breaker keeps nodes from being compared
    while len(heap) > 1:                                   # D. greedy merging
        f1, _, left = heapq.heappop(heap)                  # smallest
        f2, _, right = heapq.heappop(heap)                 # second smallest
        heapq.heappush(heap, (f1 + f2, order, HuffNode(None, f1 + f2, left, right)))
        order += 1
    return heap[0][2]

def generate_codes(node, prefix="", codes=None):           # E. code generation
    if codes is None:
        codes = {}
    if node is None:
        return codes
    if node.left is None and node.right is None:           # leaf
        codes[node.char] = prefix or "0"                   # single-character input gets code "0"
        return codes
    generate_codes(node.left, prefix + "0", codes)         # left branch = 0
    generate_codes(node.right, prefix + "1", codes)        # right branch = 1
    return codes

def encode(text, codes):                                   # F. encoding
    return "".join(codes[ch] for ch in text)

def decode(bits, root):                                    # G. decoding
    if root is None:
        return ""
    if root.left is None and root.right is None:           # only one distinct character
        return root.char * len(bits)
    result, node = [], root
    for bit in bits:
        node = node.left if bit == "0" else node.right
        if node.left is None and node.right is None:       # reached a leaf
            result.append(node.char)
            node = root                                    # go back to the root
    return "".join(result)

C. Frequently asked questions

What is an expression tree in data structures?

An expression tree is a binary tree that represents an arithmetic expression. Operands are stored in leaf nodes and operators in internal nodes, so the shape of the tree shows the order of evaluation.

How do I build an expression tree in Python?

Convert the expression to postfix, then scan it with a stack: push each operand as a leaf, and for each operator pop two nodes, make them the children of a new operator node and push that node back. The last node left is the root.

What is Huffman coding used for?

Huffman coding is a lossless compression algorithm. It assigns shorter bit codes to frequent characters and is used inside systems such as DEFLATE (ZIP, gzip, PNG) and JPEG, usually together with other techniques.

Why is Huffman coding a greedy algorithm?

Because it always merges the two nodes with the smallest frequencies. This locally best choice can be proved to give an optimal prefix code, so no backtracking is needed.

What is the time complexity of the Huffman coding algorithm?

Building the tree takes O(k log k) for k distinct characters, counting frequencies takes O(n), and encoding takes O(n), so the whole process is about O(n + k log k).

E. Key takeaways

Remember
  • Expression tree: a full binary tree; operands are leaves, operators are internal nodes.
  • Notations: inorder → infix (needs parentheses), preorder → prefix, postorder → postfix.
  • Construction: scan postfix left to right (or prefix right to left) with a stack; pop right child first for postfix.
  • Evaluation: recursive postorder: children first, operator last. O(n) time.
  • Huffman tree: repeatedly merge the two lowest-frequency nodes using a min-heap; left = 0, right = 1.
  • Greedy and prefix-free: the local choice is optimal, and codes on leaves never clash, so decoding is unambiguous.
  • Lossless: Huffman decoding recreates the exact original. Real systems use it as one stage of a larger method.

F. Conclusion

Expression trees and Huffman coding show how much work a simple binary tree can do. One tree turns a line of text into something a computer can evaluate, optimise and translate. The other turns raw character counts into a compact, decodable code. Together they use stacks, heaps, recursion and traversals, the building blocks of nearly every DSA topic.
